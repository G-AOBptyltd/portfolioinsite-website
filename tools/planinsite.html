🟠 Jira CSV Export — Recommended JQL

In Jira, go to Issues → Search for Issues, switch to Advanced search, paste the query below (replace <project name> with your project key), then export via Export → CSV (all fields):

project = <project name> AND sprint in (futureSprints(), openSprints(), closedSprints()) AND updated >= -16w ORDER BY created DESC

The -16w filter limits results to items updated in the last 16 weeks. Adjust to control export size.

📐 How PlanInSite Velocity is Calculated

PlanInSite uses team throughput for PI and sprint planning because planning is a team commitment decision.

Team Velocity = total completed team SP ÷ number of relevant historical sprints
PI Capacity = Team Velocity × PI sprint count

Example: Vanguard velocity = 110 SP/sprint × 5 sprints = 550 SP PI capacity. Only completed (Done/Resolved/Closed) work counts toward velocity.

🔑 Sprint divisor vs Sprints per PI — they are different

The sprint divisor (Velocity Baseline) is the historical averaging window — how many past sprints you divide delivered points by to get average velocity. Sprints per PI (Config) is the forward planning horizon that multiplies velocity into PI capacity. Setting one no longer changes the other.

✎ Manual velocity override

Velocity is calculated from the baseline by default. To override it for a team, use Edit on Teams & Capacity — set avg velocity and sprints per PI directly, and tick Lock so Apply Baseline won't overwrite your manual figures. Locked teams show a "✎ manual" marker.

⚖️ Why this may differ from FlowInSite

FlowInSite sums each person's individual average delivered SP per participated sprint. That is useful for diagnosing team-member contribution and trends — but it is not the same as aggregate team throughput.

Use PlanInSite velocity as the planning baseline. Cross-check with FlowInSite if the current named team differs materially from the historical team, or if FlowInSite shows new joiners, absences, or falling trends. Prefer the most recent 4–6 normal delivery sprints and exclude practice sprints, IP sprints, Kanban buckets, and holiday-affected periods.

⚙ PI Loading Levels & T-Shirt Sizing

Both live in the Config drawer (gear icon, top right).

🎯 PI Loading Levels

Choose which backlog hierarchy levels PI Loading can search and commit. The default is the planning band — Feature, Epic, SAFe Epic. Tick levels above (Initiative, Theme, Portfolio Epic) or below (Story, Task, Bug, Sub-task) only if you want them in PI Loading. This controls PI Loading only and does not affect velocity.

📐 T-Shirt Sizing — two modes

Story Points — each size (XS–XXL) maps to a fixed point value you set.

PI Planning (sprint-based) — sizes XS–XL are defined as sprint ranges and load against capacity as sprints × that team's velocity, so the points are team-specific. Keep sizing relative — compare scope, complexity and risk, not hours. XL is flagged "split before PI" as a signal to break it down.
